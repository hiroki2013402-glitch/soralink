# SoraLink

SoraLink is a responsive social photo/video sharing app built with React + TypeScript + Vite, Express, and Turso/libSQL. The app includes an OAuth login flow for Sennin Account, a home feed, text and/or media posts, post and image detail pages with comments, user search, profile pages, profile editing, follows, likes, and notifications.

## Features

- Sennin Account OAuth login/logout (no local password database)
- Responsive blue/white UI with a mobile bottom navigation
- Text-only, image, or video posts (media is optional) with delete-own-post permission
- Post detail page (`/page/post/:id`) with comments, and a full-screen image view (`/page/post/:id/image`)
- Image upload from the device; uploaded bytes are stored in Turso as 256 KiB BLOB chunks and served through `/api/media/:id`
- Video upload (up to 200 MB) in chunks to a separate Turso database, with a custom video player
- Direct messages with text and photos, plus 24-hour notes (Supabase)
- Separate URL paths for `/page/login`, `/page/home`, `/page/search`, `/page/create`, `/page/notifications`, `/page/profile`, `/page/post/:id`, and `/page/post/:id/image`
- Clickable follower/following counts with user lists and profile navigation
- Profile page with avatar, cover image, bio, website, posts, follower/following counts
- User search, follow/unfollow, like/unlike
- Notifications for new likes and follows
- Turso schema initialization and backward-compatible profile-column migrations
- Production static serving from the same Express process

## Requirements

- Node.js 20+
- A Turso database and auth token
- An OAuth application registered in Sennin Account
- Turso database and auth token; images are stored in Turso, so monitor database storage and read/write usage. Images are limited to 20 MB per file.
- Supabase project (direct messages and notes); a separate Turso database is required only if video uploads are needed

## Source layout

- `server/`: Express API, OAuth, database schema and media storage.
- `src/pages/`: one file per screen (see `src/pages/README.md`); `AppPage.tsx` is the signed-in shell.
- `src/components/`: reusable UI; `src/components/layout/` holds the top bar, side/bottom navigation and right rail.
- `src/lib/`: API client, route parsing, formatting, image resizing and error helpers.

## Local setup

1. Copy `.env.example` to `.env`.
2. Fill in all required values below.
3. Install dependencies: `npm install`
4. Build: `npm run build`
5. Start production mode: `npm start`

For development with Vite hot reload, use `npm run dev`. Vite proxies `/api` requests to `http://localhost:3000`.

## Required environment variables

| Variable | Purpose |
|---|---|
| `COOKIE_SECRET` | Random secret, at least 32 characters |
| `TURSO_DATABASE_URL` | Turso database URL (`libsql://...`) |
| `TURSO_AUTH_TOKEN` | Turso auth token |
| `SENNIN_CLIENT_ID` | OAuth client ID from Sennin Account |
| `SENNIN_REDIRECT_URI` | Exact callback URL, usually `https://YOUR-SERVICE.onrender.com/api/auth/callback` |

Configure `APP_ORIGIN` to the public origin of the frontend/service. For a single Render web service, use the same Render URL, e.g. `https://YOUR-SERVICE.onrender.com`. The optional OAuth endpoints and client secret are documented in `.env.example`.

## Render deployment

Deploy this folder as a Node web service:

- **Build Command:** `npm install && npm run build`
- **Start Command:** `npm start`
- **Health check path:** `/api/health`

The server serves the built frontend from `dist` when it is present; this does not depend on `NODE_ENV`.

Add the environment variables in Render's Environment settings. Set `SENNIN_REDIRECT_URI` to the exact deployed callback URL and register that same URI in the Sennin Account OAuth app. Do not commit `.env` or database tokens.

## Media uploads and storage

Images are uploaded directly from the device. The server checks allowed MIME types and file signatures, enforces a 20 MB limit, and stores the bytes in `media_chunks` as 256 KiB BLOB chunks in Turso. `media_assets` stores the metadata. `/api/media/:id` streams the stored file back to the browser. New posts accept only image IDs generated by this upload endpoint, and a user can only attach media they uploaded. A post may have text, media, or both. Videos are stored in the separate video-only Turso database (see the next section).

This keeps the app self-contained, but media can consume Turso storage and read/write quota quickly. For a large public social network, object storage such as S3-compatible storage is usually more economical; this version intentionally uses Turso as requested. Avatar and cover images can now be uploaded from the profile editor. The website field remains a normal profile link.

## Video storage (R2-free)

Video binary data is stored in a **separate Turso database** from the app's main database. To enable video uploads, configure `VIDEO_TURSO_DATABASE_URL` and `VIDEO_TURSO_AUTH_TOKEN` with credentials for a new database created specifically for video chunks. Keep `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` for the existing application database. Do not point both pairs at the same database if you want data isolated. If the video database is missing or cannot be reached at startup, the app still starts, but video endpoints return HTTP 503 until the video database is configured and the service is restarted. The startup log includes the database connection error, and `/api/health` reports `videoStorage: "unavailable"`.

The browser uploads each video as 256 KiB binary chunks to the application server; the server writes each chunk to the dedicated video database. Playback supports HTTP byte ranges so the player can seek and buffer portions of the file. R2 credentials and buckets are not required. The upload limit is 200 MB per video, but actual capacity and write limits depend on your Turso plan. Large videos can use substantial database storage and write usage, so check your plan before opening uploads to many users.

Setup:
1. In Turso, create a separate database for videos (for example `soralink-videos`).
2. Create an auth token for that database.
3. Set `VIDEO_TURSO_DATABASE_URL` and `VIDEO_TURSO_AUTH_TOKEN` in Render's environment variables.
4. Keep the existing main database variables unchanged, then redeploy.


## Database behavior

On startup, the server creates missing tables and indexes. Existing `users` tables are migrated to add `cover_url`, `bio`, and `website` if those columns do not exist. On first start after this version, the `posts` table is rebuilt once so `media_type` and `media_url` become nullable (text-only posts). Likes are copied aside and restored in the same transaction. The `comments` table is created automatically.

Stories were removed from the app. The `stories` table is no longer created or read; existing rows are left in place and can be dropped manually once you no longer need them.

## Troubleshooting

- `TURSO_DATABASE_URL と TURSO_AUTH_TOKEN を設定してください`: set both Render environment variables.
- OAuth callback error: verify client ID, redirect URI exact match, authorization/token/userinfo endpoints, and `APP_ORIGIN`.
- Image upload errors: check that the file is a supported image, is no larger than 20 MB, and that Turso has sufficient storage and request quota.
- Video upload errors: check `VIDEO_TURSO_DATABASE_URL` and `VIDEO_TURSO_AUTH_TOKEN`, the video database capacity/write limits, and that the file is MP4, WebM or MOV and no larger than 200 MB.
- Videos not playing: check that the video-only Turso database credentials are correct and that all video chunks were uploaded.
- Images not appearing: verify that `/api/media/:id` returns the stored content and the media rows/chunks exist in Turso.
- `npm start` cannot find `dist-server/index.js`: run the build command successfully before starting.


## Structure

- `src/pages/`: route-aware page composition (`AppPage.tsx`) and the extracted `login/LoginPage.tsx`; URL routes are documented above
- `src/components/`: reusable UI pieces such as post composer, media post, and brand mark
- `src/lib/`: API client helpers
- `server/`: OAuth, session security, API routes, and database initialization

## Security notes

- OAuth state validation and PKCE remain enabled; session cookies are HttpOnly and SameSite=Lax.
- Helmet security headers and a restrictive Content Security Policy are enabled.
- API request bodies are size-limited and API routes have per-process rate limits.
- Uploads are authenticated, limited by file size and allowed media signatures, and ownership is checked before media can be attached to posts or profiles. Never commit `.env` or production secrets.
- The included rate limiter is in-memory and is not shared across multiple server instances; use a shared rate-limit store for horizontally scaled production deployments.

## UI direction

The feed uses an X-style layout: white cards with a left avatar column, a modern composer with a character ring, and a compact top bar with the SoraLink logo. Navigation is responsive, with a bottom bar on phones. SoraLink retains its own name and logo rather than copying Facebook branding or assets.

## Direct messages (Supabase)

Direct messages use Supabase for their database and Realtime; everything else (users, posts, notifications) stays in Turso.

- Supports 1:1 chats and group chats (up to 20 people). Messages can be text (up to 1000 characters) or photos (JPG, PNG, WebP, GIF, up to 10 MB).
- Notes: a 60-character status shown above your avatar in the message list for 24 hours. Visible to people you follow and your followers. Tapping someone's note opens a chat with them.
- The inbox and chat follow Instagram's layout: notes row, unread dots, sent and received bubbles, time separators, and a "new message" sheet.
- Images are stored in the private `dm-images` Storage bucket and served through `/api/dm/messages/:id/image` as short-lived signed URLs.
- Browsers receive new messages through Supabase Realtime. Row Level Security limits each browser to its own conversations, using a short-lived JWT that the server issues.
- The nav badges show the number of unread notifications and unread messages (polled every 30 seconds, and updated live for messages).

Setup:

1. In the Supabase SQL Editor, run `supabase/schema.sql`. It is safe to run on an existing database: it adds text messages, conversation previews and the notes table.
2. Add `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_JWT_SECRET` to the environment (Project Settings → API). The service role key must stay on the server only.
3. Run `npm install` before building, since `@supabase/supabase-js` was added.

Realtime tokens are signed with the project's legacy JWT secret (HS256). If the project uses asymmetric JWT signing keys, update `mintRealtimeToken` in `server/supabase.ts` to match.

## Mentions, hashtags, polls, and image thumbnails

- **@mention**: type `@` plus a display name in a post. The composer suggests matching people. A mention links to that profile only when the name matches an existing user (names without spaces). Mentions are stored with the post (`post_mentions`). Captions only; comments are plain text.
- **#hashtag**: any `#word` in a caption is stored (`post_hashtags`, lower-cased). Tapping one, or searching `#word`, lists the visible posts with that tag.
- **Polls**: text-only posts can carry 2 to 4 options (`poll_options`, `poll_votes`). One vote per person; voting again moves the vote. Results show after voting.
- **Images**: photos above 700 KB also upload a 720px copy (`media_assets.thumb_id`). The feed loads that copy (`/api/media/:id?size=thumb`), and the full image opens on tap. The server caches recently read media in memory (up to 96 MB) and sends ETags, so repeat views skip the Turso chunk reads.
- Notices and announcements float over the page, so they no longer push the DM or the feed around.

## Admin area (/admin)

Open `/admin` and enter `ADMIN_PASSWORD`. Then sign in with the Sennin Account you want to make admin. That login (and only that login, within 15 minutes of the password check) grants admin rights for 12 hours or until logout. If `ADMIN_SENNIN_ID` is set, only that account can be granted.

Admins can:
- **Users**: search accounts, open each user's settings screen, suspend or restore an account (suspending also ends all its sessions), see their posts, and jump to their DMs.
- **Posts**: search every post, edit the text and visibility, or delete a post.
- **Announcements**: publish a site-wide notice. It appears as a banner for every signed-in user until they close it.
- **DM**: read every conversation (text and photos, read-only). Every page view is recorded.
- **Audit log**: every admin action above is recorded with the admin's name and time.

Setup: add `ADMIN_PASSWORD` (use a long random value) and, recommended, `ADMIN_SENNIN_ID` to the environment, then restart. The `sessions.is_admin`, `users.banned_at` / `banned_reason`, `admin_audit` and `announcements` tables are created or migrated on startup.

## Post visibility, close friends, and search

- Each post has a visibility: **公開** (everyone), **フォロワーのみ** (followers of the author), or **親しい友達** (close friends chosen by the author).
- Close friends are picked from the author's followers in the 親しい友達 settings (profile page). Unfollowing removes that person from the close friends list.
- Visibility is enforced on the server everywhere: feed, post detail, comments, likes, profiles, recommendations, search, and post media (`/api/media/:id`). Restricted media is served with `Cache-Control: private`.
- Search (`/api/search`) covers people and post text. The search box shows suggestions as you type (`/api/search/suggest`).
- Existing posts are public after the migration. The `visibility` column is added automatically on startup.
